## 二、板卡到货与验收

### 2.1 选型变化

原定 60K 版本，最终买入 **ACG720-138K**（二手，585 元包邮）。

器件 GW5AST-138，PG484，**Device Version C**，138240 LUT4，6120 Kbit 块 RAM。资源是 60K 的 2.3 倍。

同板有 AE350 硬核，**明确不用**，理由见 `docs/decisions/0001-不使用AE350硬核.md`。

### 2.2 例程筛选

资料包里三个 DDR 章节逐一核对工程文件里的器件型号：

| 章 | 工程器件 | 结论 |
| --- | --- | --- |
| 第 36 章 | `GW5AST-LV138FPG676AES` | 封装不对；且 `DRAM_NUM=2`，IP 按 32 位 DQ 生成 |
| 第 37 章 | `GW5AT-LV138PG484AC1/I0` | 无 `.cst`，纯仿真例程 |
| 第 38 章 | `GW5AT-LV138PG484AC1/I0` | 可用，`.cst` 与通用管脚表逐条一致 |

以第 38 章的 IP 和约束为基础，只新写顶层，做了一个最小验证工程：写 16 拍 128 位再读回比对，三个 LED 分别指示 PLL 锁定、初始化完成、读写正确。

### 2.3 两个关键问题

完整排查过程见 `docs/bugs/0001-DDR3初始化失败与复位时序.md`，这里只记结论：

| 问题 | 根因 | 修法 |
| --- | --- | --- |
| 初始化要 60 秒 | 料包的加密 IP 是按 Version B 生成的，板上是 C 版 | 用 IP Core Generator 按本机器件重新生成 |
| 按键复位后初始化起不来 | IP 复位释放与 200MHz 起始同拍 | PLL 锁定后再数 256 拍才释放复位 |

### 2.4 验收结果

| 项 | 结果 |
| --- | --- |
| JTAG 识别 | 通过，GW5AST-138，Version C |
| 点灯 | 通过 |
| DDR3 初始化 | 上电 6 秒内，按键复位后同样 |
| DDR3 读写 | 16 拍写入后逐拍读回，数据全一致 |
| 复位 | 按键复位功能正常 |
| 结论 | 可用，已确认收货 |

### 2.5 顺带确认的架构参数

DDR3 是 16 位颗粒、256 MB，用户接口固定 128 位（1:4 时钟比）。三个独立来源印证：通用管脚表、第 38 章约束文件、Gowin IP 参数窗口。据此确定需要写 128→32 窄化层，见 `docs/decisions/0002-ddr3位宽与AXI数据宽.md`。

## 四、HDLBits Verification 收获

前面的 HDLBits 题目练的是「写电路」，Verification 这一部分练的是「验电路」——用 Verilog 写 testbench，给 DUT 灌激励、观察输出是否等于预期。

### 写 TB 的基本套路

| 元素 | 怎么写 | 为什么 |
| --- | --- | --- |
| 激励信号 | 声明成 `reg` | 只有 `reg` 能在 `initial` / `always` 里赋值 |
| 观察对象 | 保持 `wire` | DUT 输出由 DUT 驱动，TB 只读 |
| 时钟 | `initial begin clk = 0; forever #5 clk = ~clk; end` | 每 5 个时间单位翻转，周期 10 |
| 延时 | `#10` | 从当前时刻往后推 10 个时间单位 |
| 打印 | `$display` / `$monitor` | 前者执行到才打印，后者信号一变就打印 |
| 结束 | `$finish` | 不写的话 `forever` 时钟一直跑 |

### 一处澄清：`#` 的单位不是时钟周期

`#10` 里的 10 是**时间单位**，由 `` `timescale 1ns/1ps `` 定义，与时钟无关。

`#10` 在同一份文件里永远等于 10 ns，而时钟周期由 `forever #5` 决定。两者只是碰巧对上——习惯上把周期设成 10 的整数倍，于是 `#10` 看起来像一个周期。改成 `forever #2`，周期变 4 ns，`#10` 就是 2.5 个周期。

### 和项目里 C++ TB 的对照

| | HDLBits 的 Verilog TB | 项目里的 C++ TB |
| --- | --- | --- |
| 推进时间 | `#10` 延时 | 手写 `tick()`，时间是自己维护的整数 |
| 时钟 | `forever #5` 自动跑 | 每次 `tick()` 手动翻两次 |
| 判定 | `$display` 打印，人眼看 | `if (dut->z != zs[i])` 自动比 |
| 结束 | `$finish` | `return errors ? 1 : 0` |

Verilator 不支持 `#delay`——它把 Verilog 编译成 C++，没有「等 10 ns」这回事，时间只能由 TB 自己数。

### 激励不要在时钟沿上跳变

同一时刻时钟在翻、输入也在变，执行顺序不确定。稳妥做法是错开，比如沿前 1 ns 赋值。这个习惯写 AXI 激励时会直接用上——`VALID` 不能贴着采样沿跳变。

Verification 刷完就停。语法与 TB 基本写法已经够用，剩下的题是重复练手，时间要挪给协议和真正的设计。

## 六、心得

**1. 反证实验看到了什么**

把 `assign z` 从 `(state == S3)` 改成 `(state == S2) && x` 之后，`verilator --lint-only` 依然零输出，但 TB 从第 3 拍开始全红。

这说明 lint 与仿真管的不是一件事：lint 做静态检查（语法、位宽、多驱动、latch 推断、不可综合写法），能查出「写得不对」，查不出「行为不对」。

第 3 拍报错的原因：那一拍 `state` 是 S2、`x` 是 1，Mealy 式的输出当场为 1，而期望是 0。Moore 与 Mealy 的差别就在这一拍显形。

**2. 「仿真能看到」与「TB 能断言」差在哪**

GTKWave 里能调出 `state`、`next_state`，因为 VCD 记录的是仿真器内部所有信号。但写 C++ TB 时，Verilator 只把顶层端口暴露成类的公开成员，`dut->state` 根本不存在。

而即使能访问，也不该访问：**断言内部状态等于让测试依赖实现细节**。哪天把状态重新编码成 one-hot，所有基于 `state` 的断言会全线崩掉，可模块对外行为一点没变。

状态是实现手段，不是功能定义。

**3. 测试用例长度与循环边界**

数组长度、循环边界、常量三处必须同源，用 `const int N` 控制。

循环比数组长会越界读垃圾内存；**循环比数组短则更阴——后面的用例静默不跑，TB 依然报 PASS**，以为测了十个用例，实际只跑了六个。

**4. 板卡验收里最值得记的一件事**

「例程能跑」不等于「例程写对了」。

第 38 章的 DDR3 例程把 IP 复位接在按键上，看起来正常工作。但换一个动作（按按键复位）就暴露了：IP 的复位必须在时钟稳定之后释放。例程不是做对了，是没触发那个约束。

这一类问题只在换条件时暴露。所以拿到别人的东西，除了「能不能跑」，更该问「它为什么在这个条件下没问题」。
