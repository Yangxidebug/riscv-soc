## 三、HDLBits Verification 收获

前面的 HDLBits 题目练的是「写电路」，Verification 这一部分练的是「验电路」——用 Verilog 写 testbench，给 DUT 灌激励、观察输出是否等于预期。

### 写 TB 的基本套路

| 元素 | 怎么写 | 为什么 |
| --- | --- | --- |
| 激励信号 | 声明成 `reg` | 只有 `reg` 能在 `initial` / `always` 里赋值，`wire` 不行 |
| 观察对象 | 保持 `wire` | DUT 的输出由 DUT 驱动，TB 只读不写 |
| 时钟 | `initial begin clk = 0; forever #5 clk = ~clk; end` | 每 5 个时间单位翻转一次，周期 10 |
| 延时 | `#10` | 从当前时刻往后推 10 个时间单位 |
| 打印 | `$display` / `$monitor` | 前者执行到那一行才打印，后者信号一变就打印 |
| 结束 | `$finish` | 不写的话 `forever` 的时钟一直跑，仿真器不退出 |

### 一处澄清：`#` 的单位不是时钟周期

`#10` 里的 10 是**时间单位**，由文件头的 `` `timescale 1ns/1ps `` 定义，与时钟无关。

- 在 `timescale 1ns/1ps` 下，`#10` 就是 10 ns；
- 时钟周期由 `forever #5` 决定，半周期 5 ns，整周期 10 ns。

两者只是**碰巧对上**。习惯上把时钟周期设成 10 的整数倍，于是 `#10` 看起来像「一个周期」。若改成 `forever #2`，周期变成 4 ns，`#10` 就是 2.5 个周期——`#` 的数值一点没变。

### 和项目里 C++ TB 的对照

| | HDLBits 的 Verilog TB | 项目里的 C++ TB |
| --- | --- | --- |
| 推进时间 | `#10` 延时 | 手写 `tick()`，时间是自己维护的整数 `t` |
| 时钟 | `forever #5` 自动跑 | 每次 `tick()` 手动翻两次 |
| 判定 | `$display` 打印，人眼看 | `if (dut->z != zs[i])` 自动比 |
| 结束 | `$finish` | `return errors ? 1 : 0` |

概念相同：给激励 → 等时间 → 看输出。差别在 Verilator 不支持 `#delay`——它把 Verilog 编译成 C++，没有「等 10 ns」这回事，所以时间只能由 TB 自己数。

### 一个问题：激励不要在时钟沿上跳变

```verilog
always #5 clk = ~clk;

initial begin
    #10 x = 1;    // 10ns 正好压在上升沿，产生竞争
end
```

同一时刻时钟在翻、输入也在变，执行顺序不确定，不同仿真器可能给出不同结果。稳妥做法是错开一点，比如 `#9 x = 1;`。

这个习惯以后写 AXI 激励时会直接用上——`VALID` 不能贴着采样沿跳变。

## 四、心得

**1. 反证实验看到了什么**

把 `assign z` 从 `(state == S3)` 改成 `(state == S2) && x` 之后，`verilator --lint-only` 依然零输出，但 TB 从第 3 拍开始全红。

这说明 lint 与仿真管的不是一件事：lint 做静态检查（语法、位宽、多驱动、latch 推断、不可综合写法），能查出「写得不对」，查不出「行为不对」。功能对不对必须跑起来才知道。

第 3 拍报错的原因也清楚了：那一拍 `state` 是 S2、`x` 是 1，Mealy 式的输出当场为 1，而期望是 0。Moore 与 Mealy 的差别就在这一拍显形——一个等状态跳过去，一个同步命中。

**2. 「仿真能看到」与「TB 能断言」差在哪**

GTKWave 里能调出 `state`、`next_state` 甚至 `S0`~`S3` 的波形，因为 VCD 记录的是仿真器内部所有信号。

但写 C++ TB 时，Verilator 只把顶层端口暴露成类的公开成员，`dut->state` 根本不存在。想访问得加 `--public-flat-rw` 编译，让 Verilator 关掉部分优化。

而即使能访问，也不该访问：**断言内部状态等于让测试依赖实现细节**。哪天把 4 个状态重新编码成 one-hot，或者合并两个状态，所有基于 `state` 的断言会全线崩掉，可模块对外行为一点没变。

状态是实现手段，不是功能定义。功能测试只盯模块在给定激励下的输出是否符合预期，内部怎么走不关心。

**3. 测试用例长度与循环边界**

数组长度、循环边界、常量三处必须同源，用 `const int N` 控制。

两种错法后果不同：循环比数组长会越界读垃圾内存，行为不可预测；**循环比数组短则更阴——后面的用例静默不跑，TB 依然报 PASS**，以为测了十个用例，实际只跑了六个，可能导致我们对模块行为的误判。
